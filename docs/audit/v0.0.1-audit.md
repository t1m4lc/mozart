### A1.5 — A workspace is created

**Status :** ⚠️ partial (manual only, naming and branch policy off-spec)

**Actual behavior :** Triggered from the project row's `+` button
or context menu — **not** auto on project add. Flow :
`createWorkspace(projectId)` → `WorkspacesFacade.createForPrompt`

1. Generate name via `generateWorkspaceName(taken)` — pool of 10

2. Insert a `pending: true` ghost row in the store.
3. Resolve base branch via `adapter.listBranches(project.path)` →
   prefer `'main'` else first branch.
4. `adapter.create({ projectId, baseBranch, taskText: 'none',
   workspaceName })` — Tauri `create_workspace` →
   `workspace_service::create_workspace`.
5. On success : swap ghost for real, set active, navigate to
   `/workspaces/:id`.

Branch name is hardcoded server-side. Per
`src-tauri/src/commands/mod.rs:305-307` comment :
"Intentionally does NOT touch `branch_name` — the branch is
derived from the original name at create time and never re-derived
(vocabulary contract)". The branch prefix is `agent/<slug>` per
schema 001 comment.

**Expected per plan.md :** Phase 1 — auto-create on project add ;
name `{artist}-{N}` (already curated) ; branch
`{github-username}/{workspace-name}` when GitHub connected, else
`mozart/{workspace-name}` ; create first chat named `"Start"` ;
detect package manager and run install.

**Gap / notes :**
- No auto-creation on project add.
- Pool of singers is fine but `taskText: 'none'` is a placeholder ;
  Phase 1 wants the workspace ready for chat.
- Branch prefix is `agent/`, not `mozart/` or
  `{github-user}/{workspace-name}`. **Blocking for Phase 1 spec.**
- First chat is created lazily by `ChatFacade.hydrate` with title
  `'Untitled'` (`chat.facade.ts:97`), not `'Start'`.
- No package-manager detection, no `npm install`.

### A1.8 — User triggers an agent turn (does it stream? does it edit files?)

**Status :** ✅ works (with caveats around UI polish)

**Actual behavior :** `_runAssistantTurn` calls
`LLM_ADAPTER.stream({ workspaceId, history, mode })` →
`TauriLlmAdapter.stream`
(`domains/llm-model/data/tauri-llm.adapter.ts`). This :

1. Registers a `Channel<StreamEvent>` and a listener on the typed
   event `agentRunTerminated`.
2. Calls `commands.startAgentRun(workspaceId, lastPrompt, channel)`
   (`src-tauri/src/commands/mod.rs:402-432`).
3. The Rust side spawns the `claude` CLI in the workspace's
   worktree path via `claude_cli::runner::spawn_run`
   (`src-tauri/src/claude_cli/runner.rs:1-100`). Argv :
   `[-p, prompt, --output-format=stream-json,
   --include-partial-messages, --verbose]`.
4. stdout is parsed line-by-line via
   `claude_cli::parser::parse_line` into `StreamEvent` variants
   (`stream_token | tool_call | cli_output | status_update | error`)
   and pushed both to `agent_events` SQLite and to the front via
   the channel.
5. TS side translates each `StreamEvent` to `AgentEvent`
   (`tauri-llm.adapter.ts:131-162`).
6. The chat facade pipes each `AgentEvent` through the pure reducer
   `applyAgentEvent` (`chat/data/agent-stream-parser.ts:47-161`)
   which builds a `TimelineTurn` (`@mozart/ui/timeline` types) on
   the message.
7. Termination : the Rust side emits `agentRunTerminated{
   run_id, status: 'done'|'stopped'|'error'|'crashed' }` (typed
   tauri-specta event). The TS adapter pushes the corresponding
   terminal `AgentEvent` and closes the iterator.

The Rust runner runs `claude` inside the worktree path, so
**files do get edited on disk in real time** (validated structurally
— `runner.rs` uses `workspace.worktree_path` as CWD ; the agent's
tool calls hit the worktree). Pre-spawn checkpoint via
`sandbox::git_checkpoint` ; post-exit diff via
`sandbox::capture_diff` (`runner.rs` doc comment).

**Expected per plan.md :** Phase 3a — agent edits files on disk ;
text streams cleanly with a proper anchor / viewmodel scroll
pattern (no ad-hoc scroll patches).

**Gap / notes :**
- The streaming + file editing pipeline works end-to-end.
- The Timeline renders via `HlmTimeline`
  (`libs/ui/timeline/src/lib/hlm-timeline.ts`) — the user has
  flagged this as visually broken (collapse arrows misaligned).
  Phase 3a says **remove for now** and render raw text only.
- Scroll handling is **the ad-hoc patch the plan calls out** :
  `FeatureChatPanel`'s `effect()` measures the last item's
  bounding rect and calls `container.scrollBy()` to keep it at 70 %
  viewport height (`feature-chat-panel.ts:82-112`). No anchor /
  IntersectionObserver / viewmodel signal. Phase 3a must replace
  this.

**Files involved :**
`domains/chat/data/chat.facade.ts:249-335`,
`domains/llm-model/data/tauri-llm.adapter.ts`,
`domains/chat/data/agent-stream-parser.ts`,
`domains/chat/feature-chat-panel/feature-chat-panel.ts:66-112`,
`src-tauri/src/claude_cli/runner.rs`,
`src-tauri/src/commands/mod.rs:402-472`.

## A2 — Spec-vs-reality drift

### A2.1 — `projects` vs `repos` table naming

**Spec says :** Phase 1 §"New schema / migrations needed" :
`CREATE TABLE projects (id, name, path, github_owner, github_repo,
added_at)`.

**Code does :** `001_init.sql` defines `CREATE TABLE repos
(repo_id, path, display_name, added_at, …)`, and `002` adds
`icon`, `hidden`, `sort_index`. No `github_owner` / `github_repo`
columns. The Angular side maps `repo_id → Project.id`,
`display_name → name` via `project.adapter.ts:1-14`.

**Impact :** Naming impedance ("repo" on the wire, "project" in
the UI) — already handled by the DTO mapper, no blocker. The
**missing GitHub columns** ARE a blocker for the Phase 1
"Initialize project" dialog (A1.3) and for the `{github-user}/`
branch prefix (A1.5).

**Recommendation :** Keep `repos` table name as-is (vocabulary is
correctly isolated to the DTO). Add `github_owner` and
`github_repo` columns (or a dedicated `github_link` table) before
Phase 1's GitHub flow ships.

### A2.2 — Workspace columns vs spec

**Spec says :** Phase 1 :
`workspaces(id, task_id UNIQUE, name, branch, base_branch, status,
worktree_path, created_at)`.

**Code does :** `001_init.sql` +
the `patch_workspaces_columns` idempotent guard in `db/mod.rs`
produce :

```
workspace_id, task_id (NOT UNIQUE), name, worktree_path UNIQUE,
branch_name, base_branch, status, pinned, unread, ui_status,
created_at, deletion_intent
```

Differences :

- `branch` vs `branch_name` — internal-only, fine.
- `task_id` is **not** UNIQUE in 001 (the plan says 1:1 task ↔
  workspace ; the schema is already 1:N-ready, which is the
  v1.0.0 target). Not a blocker.
- Extra columns `pinned`, `unread`, `ui_status`, `deletion_intent` —
  additive ; some predate Phase 1's spec (notably `ui_status` for
  a kanban column, which is **not in the v0.0.1 MVP plan** —
  appears to be a pre-MVP exploratory feature).

**Impact :** Additive, low risk. `ui_status` may be dead code for
the MVP — the kanban view it implies doesn't exist in the plan.

**Recommendation :** Keep. Consider documenting `ui_status` as
"pre-MVP exploration, not surfaced in v0.0.1 UI" so future
contributors don't assume it's load-bearing.

### A2.3 — `chats` schema vs Phase 2 spec

**Spec says :** Phase 2 §"Database migrations summary" :
`ALTER TABLE chats ADD COLUMN mode TEXT NOT NULL DEFAULT 'agent'`,
`ADD COLUMN title TEXT`,
`ADD COLUMN last_read_message_id TEXT`. Modes :
`'agent' | 'plan' | 'ask'`.

**Code does :** `004_chat.sql` defines
`chats(chat_id, workspace_id, title TEXT NOT NULL DEFAULT
'Untitled', llm_id, closed_at, created_at)`. **No `mode` on the
chat row.** `messages(message_id, …, mode TEXT, status,
timeline_json, …)` — `mode` lives **on the message**, not the
chat. The composer's mode signal is reset per chat client-side
(transient) — see `feature-chat-panel.ts:60` (`mode = signal(…)`).

Workspace_id is **not unique** on `chats`, so the multi-chat-per-
workspace future is already permitted by the schema (`threads`
still has `workspace_id UNIQUE`, which is the legacy 1:1 link the
agent_runs FK uses).

**Impact :** Phase 2 needs three modes (`agent | plan | ask`) ; the
current type is `'normal' | 'plan'` everywhere (composer types,
message model, facade signature, parser, Rust message insert).
Adding a third mode is a typed change across 5+ files and a DB
migration. Also `last_read_message_id` is missing — needed for
the "bold workspace row on unread" feature in Phase 1.

**Recommendation :** Two coordinated changes before Phase 2 :
(a) Add a new migration that adds `chats.last_read_message_id`
(needed for Phase 1's bold-on-unread). (b) Rename `mode` values
from `normal → agent` and add `ask` everywhere — composer types,
message model, Rust DTO. Phase 2 should land the full
`agent|plan|ask` change as one slice.

### A2.5 — Stream parser location and shape

**Spec says :**
[`llm-stream-parser.md` §11](../specs/llm-stream-parser.md#11-file-layout-mozart-adapted)
— parser + reducer live in `apps/desktop/src/app/domains/llm-model/
data/stream/` with `event.types.ts`, `anthropic.parser.ts`,
`reducer.ts`, and `__fixtures__/` (5 JSON files). Pure functions
only.

**Code does :** No `stream/` subfolder exists. Files :
- `domains/llm-model/data/agent-event.model.ts` — defines
  `AgentEvent` union (the post-normalization shape).
- `domains/llm-model/data/tauri-llm.adapter.ts` — does the
  StreamEvent → AgentEvent translation **inline** in the adapter.
- `domains/chat/data/agent-stream-parser.ts` — exports
  `applyAgentEvent(message, event)` — the **reducer**, but living
  in the chat domain, not llm-model.

The Rust side does the heavy parsing : `src-tauri/src/claude_cli/
parser.rs` turns each stream-json line into `StreamEvent`. So the
"Anthropic parser" lives in Rust ; the TS side gets pre-parsed
events. This is a different architecture from what
`llm-stream-parser.md` describes (where parser is TS-side and pure).

**Impact :** The plan's expected location is empty. The parser is
in the wrong domain (chat). No fixtures. No event-types file.
Phase 3a says "keep the parser + reducer" — they exist, but they
need to be **moved + organized** before Phase 3a finishes.

**Recommendation :** During Phase 3a cleanup :
- Move `agent-stream-parser.ts` from `domains/chat/data/` to
  `domains/llm-model/data/stream/reducer.ts`.
- Extract event types into `domains/llm-model/data/stream/
  event.types.ts`.
- Add at least 2 fixtures (text-only, multi-tool-with-thinking)
  for unit testing.
- The "Anthropic parser" responsibility is **split with Rust** in
  Mozart — document this explicitly so a reader doesn't expect
  the TS side to parse SSE.

## Summary

**Working today (the hard parts)** :

- Tauri ↔ SQLite ↔ Angular hydration loop : projects + workspaces +
  chats + messages all persist, restore on boot, and the optimistic
  store + adapter discipline is clean. Specta-generated typed
  bindings work end-to-end.
- Agent run pipeline : the Claude CLI is spawned in the workspace's
  worktree, files do get edited on disk, stream events flow back via
  `Channel<StreamEvent>`, the typed `agentRunTerminated` event closes
  the loop, the reducer builds a `TimelineTurn`, and the UI
  renders it. Stop / cancel works. Queue-second-prompt-while-
  streaming works.
- Vocabulary discipline : zero "worktree" / "HEAD" / "refs/heads"
  leaks in user-facing strings. The `worktree.adapter.ts` chokepoint
  is honored.
- Facade pattern, OnPush, signal stores, intra-domain layout —
  the codebase is internally consistent and matches Convention #3.

**Critical gaps for Phase 1** :

1. **Dashboard** : `/` doesn't render the three-card flow. The
   user lands in a broken workspace shell.
2. **State coherence** : middle column + right aside render even
   without a workspace.
3. **Auto-workspace on project add** : today the workspace is
   manual.
4. **Non-git dialog** : Rust silently auto-inits ; the user-facing
   "Initialize project" dialog with optional GitHub repo creation
   is absent.
5. **Branch name policy** : hardcoded to `agent/<slug>` ; needs
   `{github-user}/{ws-name}` (or `mozart/`).
6. **First chat title** : `'Untitled'`, should be `"Start"`.
7. **Package manager install** : no detection, no execution.
8. **Sidebar Chats group** : entirely missing.
9. **Workspace row** : no streaming loader, no hover popover, no
   bold-on-unread.
10. **GitHub schema** : `repos` table has no `github_owner` /
    `github_repo` ; needed before the Open-GitHub flow ships.

**Other critical issues (for later phases, surfaced now)** :

- Phase 3a : remove `HlmTimeline` from `agent-message.ts`, replace
  the ad-hoc scroll patch in `feature-chat-panel.ts` with an
  anchor + IntersectionObserver / viewmodel signal.
- Phase 3a : move parser+reducer to
  `domains/llm-model/data/stream/`, add fixtures.
- Phase 2 : compose mode is 2-valued today (`normal | plan`),
  Phase 2 wants three (`agent | plan | ask`) ; coordinated change
  across `libs/ui/composer`, message model, Rust DTO, migration.

**Phase 1 prerequisites** : a small number of cleanup tasks need
to land before the first sub-step (dashboard cards) starts. The
proposed ordered list is the Phase B output of this audit ; see
the cleanup-tasks document once approved.
